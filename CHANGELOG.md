### Added — FBL-030 Human approval workflow

Implemented the real persisted request-to-resolution approval gate. **Operator observation of the two visual runs is pending**, so this rung's stop condition is not yet met and FBL-031 has not been started.

- `commandHandler.ts`: resolving an approval requires an **authenticated operator** (principle 14, "Humans govern"). Authenticated *agents* are refused as well — an agent resolving the gate that exists to constrain agents would make the gate ceremonial. Authorization runs before the entity lookup so a refusal cannot enumerate approval ids, and every refused caller receives an identical reason.
- **`resolvedBy` is derived from the authenticated principal, never the payload.** `event-model.md` pins it as a payload field so it must exist there, but a caller filling it in would be asserting who made a governance decision. A contradicting value is **refused rather than silently overwritten**: quietly rewriting it would leave an audit trail that disagrees with what was actually submitted.
- Duplicate resolutions are **idempotent** — the original decision, resolver, and timestamp stand, and no second event is recorded. Conflicting reversals are **rejected**: a resolved approval is an immutable decision, not a mutable field.
- `reducer.ts`: `approval.revision_requested` now creates the linked `Revision` (`sourceApprovalId`, `requestedBy: "approval"`) and moves the stage to `revision_required`, which `event-model.md` requires and which was previously unimplemented. It is **derived in the reducer from a deterministic id** rather than emitted as a second event, so one command still produces exactly one event and a full replay reconstructs the identical record. The "at most one open Revision per stage" invariant is enforced.
- `apps/api/src/main.ts`: issues a per-process operator credential alongside the agent ones, printed at startup, never persisted.
- Frontend: the approval card no longer sends `actor` or `resolvedBy` — both are now server-derived, and sending them would assert authority the payload may not carry. The operator credential is **entered by the operator and stored locally**, deliberately *not* a `NEXT_PUBLIC_*` build variable: that would put a live credential into every artifact of the build and make rotation a rebuild. A missing credential is a visible, explained disabled state, kept **distinct from the disconnected banner** so an operator can tell "not authorized" from "backend unreachable" rather than pressing a button that silently does nothing.
- **An integration break introduced by FBL-029 and fixed here:** the frontend was still sending `actor` in the body, which FBL-029's `actor_mismatch` check now rejects — the approval card was broken against the real backend. No test caught it because the browser suite runs in mock mode. The credential path replaces it properly.
- Tests: 50 new (718 total) — 28 persistence-level (every unauthorized caller class including an authority-asserting operator claim, `resolvedBy` derivation, idempotency, conflict, the pending/approve/reject/revision progression gates, the derived Revision and its determinism under replay, audit completeness, and restart durability), 9 over real HTTP (credential decides authority, SSE delivers the decision exactly once, the resolved approval is inspectable), and 13 frontend (credential gating, its separation from the disconnected state, Lighthouse attention, and credential storage).
- Verified end-to-end against the running service: no credential refused, agent credential refused, operator credential accepted, conflicting reversal refused, resolver recorded as `operator-1`.
- Verification: typecheck (8/8) and lint clean; unit + integration green (718 tests: 668 pre-existing + 50 new); production build passes; browser **341 passed / 3 skipped / 1 failed** on an isolated run — the single failure being the same already-known FBL-034-deferred flake (`shell-timeline.spec.ts:118`) seen at FBL-029, with no regression attributable to this rung. ### Added — FBL-029 Independent Inspector validation

Wired the Inspector validation path end-to-end on the real backend, per the operator-authorized sequence FBL-029–FBL-033. **Operator observation of the visual checks is pending**, so this rung's stop condition ("F-05 real-backend test green **and operator-observed**") is not yet fully met and FBL-030 has not been started.

**The gap this rung closes.** Until now the command actor was whatever the *request body* claimed, so the F-05 Inspector check — "only an Inspector may produce `stage.validation_passed`" — was satisfied by anyone willing to type `"agent-inspector"`. A guard that asks the caller who it is is not an authorization decision.

- `packages/persistence/src/principals.ts`: identity is now established by a backend-issued bearer credential. Two deliberate boundaries: the credential establishes *who*, never *what role* — the authoritative role is re-read from persisted `Agent` state at decision time, so a stolen or stale token can never assert authority its agent does not hold; and tokens are never persisted or logged, so replaying history cannot leak one. Comparison is constant-time, and an unknown token resolves to anonymous rather than to a distinguishable error, so there is no probing oracle.
- `apps/api/src/app.ts`: identity comes from `Authorization: Bearer`. A body `actor` that contradicts the credential is refused with `403 actor_mismatch` rather than silently overridden — silently ignoring it would let a caller believe it had acted as someone else, and would make the audit trail a quiet lie about what was attempted.
- `commandHandler.ts`: **authorization now runs before the entity lookup.** Otherwise the "no such BuildStage" reply is an existence oracle — an unauthorized caller could enumerate stage ids by watching which error came back. Every refused caller gets an identical reason for the same reason.
- Both outcomes require the Inspector, not only `passed`. The spec's invariant names only `validation_passed`, but a Builder able to declare its own work *failed* would still control the retry/revision path; the spec sets a floor here, not a ceiling.
- Further guards: self-certification by **evidence provenance** (an agent may not validate an artifact it created — read from `Artifact.createdByAgentId`), stage/evidence coherence, stale and out-of-order rejection, **idempotent** duplicate decisions (a retry is not a second judgement), and rejection of conflicting reversals, which require the Revision path (invariant 8).
- `reducer.ts`: an append-only `stageValidations` projection recording validator identity, authoritative role, evidence and requirement references, decision, timestamp, and resulting transition. Deliberately a **derived read model, not a new domain entity and not a payload change** — `domain-model.md` is frozen at Foundation 1.0 and `event-model.md` pins the `stage.validation_*` payloads exactly, so nothing here alters the specification. A failure is never overwritten by a later pass (principle 17).
- Frontend: QA now renders **red** on a validation failure, per `event-model.md` ("Frontend: QA red"). It previously showed orange, because a validation failure has to be carried as `blocked` — `BuildStageStatus` has no value meaning "an Inspector rejected this" — and `blocked` is also what a missing prerequisite looks like. The decision is now carried alongside the status and checked first, so a rejection is no longer displayed as a mere obstruction.
- **One design error caught by its own test:** the first cut of the independence check rejected any Inspector *assigned* to the stage under validation. But in V1 `qa_validation` **is** the Inspector's own stage (`v1-scope.md` stage 6), so assignment there is the job, not a conflict — the check made the legitimate path fail. Replaced with evidence provenance, which is what the invariant "Inspector cannot be Builder for same validation" actually names.
- Tests: 48 new (667 total) — 30 persistence-level (every rejected caller class including a role-spoofing attempt structurally identical to the real Inspector but for the credential, provenance, coherence, staleness, idempotency, conflict, the record's contents, and restart durability), 10 over real HTTP (credential decides identity; body claims refused; SSE delivers the decision exactly once; the record is inspectable), and 9 frontend (QA red vs orange, and the selectors carrying the decision).
- Verified against the running service over real HTTP: Builder credential rejected, no credential rejected with an identical reason, Inspector credential accepted, record persisted with `validatorRole: inspector`.
- Verification: typecheck (8/8) and lint clean; unit + integration green (667 tests: 619 pre-existing + 48 new); production build passes. Browser: **341 passed / 3 skipped / 1 failed** on an isolated run, the single failure being the already-known FBL-034-deferred flake (`shell-timeline.spec.ts:118` — a timeline row scrolls under the sticky header in the live feed and intercepts the click). An earlier run *while the unit suite competed for CPU* failed three different specs, all `approval-card` timeouts at 5120×1440; all 15 tests in those files pass in isolation at that same viewport, and the changed QA branch structurally cannot fire during the demo because the canonical mock script emits no `stage.validation_failed`. No regression is attributable to this rung.

### Added — FBL-027 Runtime adapter boundary

Implemented the `packages/runtime-adapters` policy boundary (ADR-006) with the `mock` adapter running behind it, per the operator-authorized bounded sequence FBL-027–FBL-028. **No real external runtime is attached** — that is FBL-028, and this rung stops short of it deliberately.

Everything is deny-by-default by construction: a policy *enumerates what is permitted*, and each evaluator answers "allowed" only when an explicit entry matches. There is no wildcard, no denylist to keep in sync, and no escape hatch.

- `packages/runtime-adapters/src/boundary.ts`: `PolicyBoundary` — the single path every runtime executes through. The mock and any real adapter differ *only* in the `ExecutionBackend` that turns an already-approved command into an outcome; policy evaluation, containment, redaction, and evidence capture are shared code rather than a convention each adapter re-implements. The whole command plan is approved before anything runs, so an allowed first command can never execute ahead of a denied second one.
- `containment/paths.ts`: containment is **physical, not lexical** — `/root/link → /etc` passes any `startsWith` test while pointing out of the sandbox, so paths are resolved with the OS before being judged. Non-existent tails are permitted (a run must be able to create files); resolution stops at the deepest existing ancestor, which cannot hide a symlink beyond it. `..` is refused outright rather than normalized, because lexical normalization and kernel resolution disagree the moment a symlink is involved. A dangling symlink is judged by its declared target, not dismissed as harmless.
- `containment/environment.ts`: the child environment is **built from nothing**, not filtered down from `process.env` — filtering fails open for every name nobody anticipated (`AWS_*`, `GH_TOKEN`, whatever the next tool invents). Variables that can redirect *which* binary runs or inject into it (`PATH`, `LD_PRELOAD`, `DYLD_INSERT_LIBRARIES`, `NODE_OPTIONS`, `GIT_SSH_COMMAND`, …) can never be allowlisted at all.
- `execution/executable.ts`: bare names resolve through the policy's declared search path, never `PATH` — otherwise whoever controls the environment decides what an allowlisted name actually runs, defeating the allowlist without textually violating it.
- `execution/processRunner.ts`: `shell: false` always; output bounded at capture time (excess counted and dropped, not buffered); timeouts terminate the **process group**, because killing only the direct child leaves grandchildren holding the sandbox's file handles while the run *looks* contained.
- `containment/commands.ts`: shell metacharacters are refused even though no shell exists. `shell: false` makes exploitation impossible; the refusal makes the *attempt* visible in evidence rather than silently inert.
- `redaction.ts` / `evidence.ts`: secrets removed by registered value and by known credential shape (provider keys, PEM blocks, bearer headers, JWTs), applied once to the whole record so a later-added field cannot be accidentally exempt. Evidence is deep-frozen (principle 18) and retained for **all four** terminal outcomes — success, failure, denial, and timeout (principle 17). Size bounding drops captured output, never the record itself, so the noisiest runs don't become the ones that vanish.
- `policy.ts`: risk classes above R2 are **unrepresentable** in the schema rather than merely checked, so principle 19 cannot be forgotten at a call site.
- Two bugs found and fixed by the tests themselves: declared roots that did not exist were silently "canonicalizing" to plausible-looking paths that bounded nothing, and the denial-code classifier misreported ordinary out-of-root paths as symlink escapes on macOS (where `/tmp` is itself a symlink).
- Tests: 103 new, covering the full FBL-027 security suite — allowed commands, unknown commands, disallowed arguments, injection attempts, absolute/relative/`..`/symlink/dangling-symlink escapes, environment leakage, secret redaction, **real** process-tree termination on timeout (asserted by checking a backgrounded grandchild's PID is dead), output bounding, evidence retention across all four outcomes, and mock-adapter interface conformance including a proof that mock and real backends produce identical denial decisions. `frontendIsolation.test.ts` structurally asserts `apps/agent-city` neither imports nor depends on this package (ADR-006).
- **Documented limitation carried into FBL-028:** `allowNetwork` is a declared and recorded policy posture, **not** kernel-level enforcement. This package creates no network namespace and installs no packet filter, so a permitted executable that opens a socket is not stopped by this boundary. V1 network denial rests on the command allowlist (no networking tool is allowlisted) and the environment allowlist (no credentials or proxy configuration reach the child). See `packages/runtime-adapters/README.md`.
- Verification: typecheck and lint clean repo-wide; full unit suite green (588 tests: 485 pre-existing + 103 new); production build passes

### Added — FBL-026 Realtime event delivery

Streamed backend events to the frontend over SSE with reconnect, snapshot reconciliation, and stale/disconnected handling, completing the operator-authorized bounded sequence FBL-023–FBL-026. **SSE was chosen over WebSockets** because delivery is strictly one-directional — commands already travel over `POST /commands` (FBL-024/025), so no bidirectional channel is required — and SSE provides browser reconnect and `Last-Event-ID` replay natively. The deterministic mock runtime remains the default and fully selectable (ADR-001); backend mode is opt-in via `NEXT_PUBLIC_FOUNDRY_API_URL`.

- `apps/api/src/eventStream.ts`: `GET /events/stream`, honoring `Last-Event-ID`/`?lastEventId=` to replay exactly the events missed during a disconnect before resuming live delivery; plus `GET /events[?since=]` for explicit reconciliation
- `packages/persistence`: `PersistenceService.subscribe()` — notifies only *after* the transaction commits, so a subscriber can never observe an event that isn't durable, and never fires for an idempotent duplicate append
- `apps/agent-city/src/lib/backend/`: `BackendClient` (SSE subscription, bounded exponential backoff capped at 15s, snapshot-plus-missed-events reconciliation on reconnect), `reconcile.ts` (duplicate-safe, order-preserving event merge), `connectionState.ts` (backoff policy, stale labeling, mutation gating), and `BackendRuntimeProvider` supplying the same `RuntimeContext` shape the mock runtime does so every existing panel and world object works against either

- Two real bugs found and fixed while testing: long-lived SSE connections made `server.close()` hang forever (now `closeAllConnections()` first, in both the service's SIGTERM path and tests), and a stream with no backlog appeared to hang until its first event (now flushes an opening SSE comment)
- Tests: 25 `apps/api` (connect/receive, backlog replay, missed-event recovery by `Last-Event-ID`, unknown-cursor full resync, duplicate-delivery safety, unsubscribe-on-disconnect, plus a `<500 ms` update-latency budget suite); 23 client-side (backoff bounds, stale labeling, mutation gating, reconnect reconciliation, out-of-order protection, duplicate safety); 10 UI (banner, disabled controls, Lighthouse disconnected precedence)

### Added — FBL-025 State machines and prerequisite enforcement

Implemented backend-authoritative transition validation for every V1 entity and command, per the operator-authorized bounded sequence FBL-023–FBL-026. `apps/api`'s command endpoint no longer denies unconditionally: a command is now applied when — and only when — it passes shape validation, its entity's transition graph, and every named invariant guard. A rejected command still leaves persisted state byte-for-byte unchanged, because `CommandHandler` never reaches `appendEvent` on the rejection path.

- `packages/persistence/src/transitionGraphs.ts`: legal status-transition graphs per entity, transcribed from each entity's documented Lifecycle and cross-checked against what `reducer.ts` actually does. Deliberately has no blanket "same status is always legal" rule — resubmitting a forward-moving command against an entity already in the target status is rejected, which is how command-level idempotency (F-09) falls out of the graph itself. The handful of genuine no-op commands (`Build.Plan`, `Upgrade.Approve`) get explicit, narrowly-scoped self-loop edges instead.
- `packages/persistence/src/commandDefinitions.ts`: maps all 82 documented commands to the single event each produces, its target entity, and its resulting status. Commands with no backing V1 event (all 8 `Task.*`, all 7 `Vehicle.*`, `Building.ChangeState`, and the various `Cancel`/`Archive`/`Reject` variants) are permanently denied with a specific reason citing why, rather than being silently invented.
- `packages/persistence/src/commandHandler.ts`: the enforcement layer. - `apps/api/src/app.ts`: `/commands` now delegates to `CommandHandler`.
