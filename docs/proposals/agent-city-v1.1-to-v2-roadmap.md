# Proposal — Agent City V1.1 to V2 Roadmap

**Type:** Product and mission-sequencing proposal. Not an active mission, implementation ladder, or authorization.  
**Date:** 2026-08-03  
**Status:** Awaiting operator review  
**Inputs:** Post-V1 truth audit, V1.1 mission proposal, V1.1 Build Ladder proposal, and the inactive Opportunity Center Future Registry entry

---

## 1. Roadmap thesis

V1 proved that a spatial world can accurately represent a governed workflow. V1.1 must prove that the same world can execute one bounded piece of real work. The releases between V1.1 and V2 should then make that real-work loop repeatable, case-oriented, externally informed, and commercially useful without jumping directly to autonomous prospecting or outreach.

The progression is capability-first:

```text
V1     Spatial architecture proof
  -> V1.1  One operator-ready real build
  -> V1.2  Repeatable bounded builds
  -> V1.3  Governed opportunity cases
  -> V1.4  Local-business discovery and website assessment pilot
  -> V1.5  Private prototype and proposal pilot
  -> V2     Governed commercial opportunity operations
```

Version labels describe product capability epochs, not deadlines. No epoch begins until its predecessor's acceptance gate is closed.

## 2. Non-negotiable laws across the roadmap

1. Backend state remains operational truth.
2. The world renders declared events; it does not invent meaningful work.
3. The Builder never validates its own output.
4. Humans approve execution with material external consequences.
5. The R0–R2 ceiling remains until a separately reviewed mission explicitly changes it.
6. Public information is collected only through approved sources and policies.
7. Evidence, provenance, confidence, and uncertainty travel with every opportunity case.
8. A prototype is private and clean-room; it does not impersonate or imply authorization from a business.
9. Outreach remains draft-only until a dedicated, audited send capability is activated.
10. Opt-outs and suppression are permanent operational constraints, not suggestions.
11. Existing V1 mock-mode regression coverage remains available.
12. Future Registry concepts do not enter an active release merely because this roadmap mentions them.

## 3. V1.1 — Operational Readiness and First Real Build

### Outcome

One operator launches Foundry with one documented command, submits one bounded software objective, reviews a plan, authorizes execution, watches backend-authoritative Architect/Builder/Inspector stages, resolves a human approval, and receives independently validated output.

### Capability earned

- Operator intent reaches the real backend.
- A backend orchestrator advances declared state machines without a second write path.
- A controlled Claude Code stage runs inside a Foundry-created disposable workspace.
- Independent tests—not the Builder—determine success.
- Restart and replay preserve operational truth.

### Explicitly not earned

- Arbitrary projects or existing repositories
- External data collection
- Multiple concurrent opportunity cases
- Public deployment
- Business outreach
- Opportunity Center activation

### Gate to V1.2

One complete real build passes the approved V1.1 acceptance suite; documentation matches implementation; Finding 6 is closed or formally carried under the operator-approved standard.

## 4. V1.2 — Repeatable Bounded Build Operations

### Outcome

Foundry can run multiple sequential bounded builds from approved templates without seed scripts, evidence collision, or manual backend commands.

### Proposed scope

- A small registry of reviewed build templates with typed objective envelopes
- Per-run disposable workspace lifecycle and immutable run identity
- Durable artifact and evidence retention without overwriting prior runs
- Queueing for sequential builds; one active real execution at a time
- Cost, duration, failure, retry, and validation summaries
- Operator cancellation, safe stop, and recovery
- Clear separation among mock, demonstration, and real modes
- A reusable adapter contract for Architect, Builder, and Inspector assignments

### Exclusions

- Arbitrary existing repositories
- Parallel autonomous builds
- External prospect discovery
- Outreach
- New districts or institutions

### Gate to V1.3

Three different bounded objectives complete sequentially; one deliberately fails validation and is repaired; restart recovery and evidence isolation pass for all three.

## 5. V1.3 — Governed Opportunity Cases

### Outcome

Foundry can manage an OpportunityCase from intake through qualification without performing web-scale discovery or external contact.

### Proposed scope

- OpportunityCase, BusinessRecord, SourceRecord, Finding, OpportunityScore, and case-state contracts
- Manual CSV/single-record intake using operator-supplied public business data
- Deduplication, provenance, confidence, and archive/disqualification reasons
- Case queue, evidence panel, decision history, and Lighthouse attention
- Compliance Agent as an independent blocking role
- Assignment of existing Architect/Builder/Inspector workers to qualified cases
- No autonomous crawling; public website URLs are operator supplied during this epoch

### World change

The Opportunity Center may appear as a locked or pilot workplace only after its active mission is approved. Its visual state represents real OpportunityCase counts and blockages, never fictional foot traffic.

### Gate to V1.4

An operator can import, review, qualify, disqualify, and archive controlled test cases with complete provenance and no external action.

## 6. V1.4 — Local Business Discovery and Website Assessment Pilot

### Outcome

For one operator-approved ZIP code and a small capped batch, Foundry discovers public small-business records, verifies official websites, and produces evidence-backed assessments.

### Proposed scope

- One approved geography per run
- Explicit source allowlist and adapter-specific terms/robots/rate-limit policy
- Strict record and request caps
- Scout Agent for public discovery with provenance
- Identity Agent for deduplication and official-domain verification
- Site Inspector Agent for approved public measurements
- Confidence thresholds and mandatory human review for ambiguous identity matches
- Accessibility, mobile, performance, security posture, SEO fundamentals, information architecture, and interaction findings
- Opportunity scoring that separates evidence from inference
- Suppression of sensitive, personal, or unsupported claims

### Exclusions

- Broad or continuous crawling
- Bypassing blocks, authentication, CAPTCHAs, or robots controls
- Contact enrichment for private individuals
- Prototype generation
- Outreach
- Automated claims about revenue impact

### Gate to V1.5

A capped pilot produces verified, deduplicated cases with reproducible assessments, source compliance evidence, and an operator-confirmed false-match rate inside the approved threshold.

## 7. V1.5 — Private Prototype and Proposal Pilot

### Outcome

For a small number of qualified, compliance-cleared OpportunityCases, Foundry creates private clean-room prototypes and human-reviewable proposal packages.

### Proposed scope

- Human prototype-authorization gate per case
- PrototypeBrief with bounded requirements and evidence-linked acceptance criteria
- Foundry-created disposable workspace
- Architect plan, Builder execution, and independent Inspector validation
- Neutral placeholder assets where business content or branding is not licensed
- Side-by-side evidence showing what changed and which measured issue it addresses
- Proposal package with assumptions, limitations, scope options, and pricing inputs
- Outreach Agent drafts only; no send adapter
- Prototype retention and deletion policy

### Exclusions

- Cloning or republishing a business's site
- Public hosting presented as official
- Modifying the real site
- Guaranteed commercial outcomes
- Autonomous pricing decisions
- Sending messages

### Gate to V2

The operator completes several private prototype cases, independently verifies their claims and quality, rejects at least one unsuitable case, and confirms that no artifact implies business authorization or public deployment.

## 8. V2 — Governed Commercial Opportunity Operations

### Proposed outcome

One operator can run a bounded local-business opportunity program in which Foundry discovers eligible public businesses, verifies identity, assesses websites, qualifies cases, creates private validated prototypes, prepares proposals, and—only after explicit human approval and compliance checks—sends individualized outreach through an audited adapter.

### V2 minimum capabilities

- Activated Opportunity Center with Scout, Identity, Site Inspector, Opportunity, Compliance, Proposal, and Outreach roles
- Reuse of Architect, Builder, and independent Inspector workers
- Bounded geographic campaigns with quotas and stop conditions
- Source-policy registry and per-adapter enforcement
- Contact-eligibility, opt-out, and suppression registry
- Human approval for each outbound message; no bulk approval by default
- Audited outreach adapter with delivery outcome and reply-state events
- Case-level evidence package accessible from every claim
- Private prototype access controls and expiration
- Cost and workload limits
- Incident stop, global pause, and adapter revocation
- Measurement of response, qualification, conversion, complaint, opt-out, and false-match rates without using those metrics to weaken safeguards

### V2 is not

- An autonomous spam engine
- A mass website-cloning system
- A lead reseller
- A system for scraping private or credentialed data
- Permission to make deceptive claims or impersonate businesses
- Permission to deploy, purchase, sign, or spend without explicit authority
- A full city expansion

### V2 definition of done

V2 is complete only when a human operator can run a small approved campaign end-to-end, every external action is attributable and reversible where possible, every contacted business passed identity/compliance checks, suppression works across restarts, prototype claims are independently validated, and no message can leave Foundry without a case-specific human approval.

## 9. Cross-release dependency map

| Capability | First introduced | Required before |
| --- | --- | --- |
| One-command real backend operation | V1.1 | Every later epoch |
| Bounded real execution in disposable workspace | V1.1 | Private prototypes |
| Independent Inspector on real output | V1.1 | V1.5 and V2 |
| Repeatable run/evidence isolation | V1.2 | Multiple opportunity cases |
| OpportunityCase and provenance graph | V1.3 | Discovery pilot |
| Compliance blocking role | V1.3 | External discovery and outreach |
| Approved source/geography adapters | V1.4 | Automated local discovery |
| Domain identity verification | V1.4 | Assessment and contact eligibility |
| Private clean-room prototype workflow | V1.5 | Commercial proposals |
| Suppression and opt-out registry | V2 | Any outbound send |
| Audited human-approved outreach adapter | V2 | External contact |

## 10. Proposed mission sequence

Each epoch requires its own reviewed mission and stable build ladder. Proposed namespaces:

| Epoch | Suggested ladder namespace |
| --- | --- |
| V1.1 | `AC-101` onward, as already proposed |
| V1.2 | `RB-201` — Repeatable Builds |
| V1.3 | `OC-301` — Opportunity Cases |
| V1.4 | `LD-401` — Local Discovery |
| V1.5 | `PP-501` — Private Prototypes |
| V2 | `CO-601` — Commercial Operations |

These identifiers are proposals only. They must not be used as active authority until the corresponding mission is reviewed and ratified.

## 11. Decisions to make later, not now

- Which public business-directory and search sources are legally and technically acceptable
- Exact geographic and batch limits
- Which jurisdictions are supported
- Whether the website assessment uses live requests, third-party measurement APIs, or both
- Contact-channel policy and business-hours rules
- Prototype retention duration and access mechanism
- Pricing model
- Whether V2 permits tightly bounded campaign-level approval or always requires message-level approval

None of these decisions should block V1.1. V1.1 builds the real-work foundation they depend on; it does not activate them.

## 12. Immediate recommendation

1. Reconcile and ratify the V1.1 mission proposal.
2. Execute V1.1 without adding Opportunity Center code.
3. Keep this roadmap and the Future Registry entry non-authoritative.
4. After V1.1 acceptance, audit whether the real-build loop is reliable enough to support V1.2.
5. Activate the Opportunity Center only through a new reviewed mission beginning with controlled case intake—not scraping or outreach.
